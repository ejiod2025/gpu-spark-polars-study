The research question

When does a complete GPU path
outperform its CPU comparison?

The experiment measures six selected TPC-H-derived queries at five scales and six complex queries at three scales. It pairs configurations within ten planned blocks, validates every successful output with independent SQL references, and retains unsupported expressions as coverage limits.

One host, fixed software and settings. Selected research workloads; not complete or certified TPC-H results.

03 / Separate descriptive extension

Two sessions, one shared host.

A coordinated same-query contention experiment examines a different condition. The isolated 400-session study remains the sole confirmatory evidence for the primary comparisons and crossover story.

Pair A

GPU Spark + CPU Polars 2.0.0

Pair B

CPU Spark + strict Polars GPU

Each process requests 26 CPU threads on the same 26-vCPU host, without disjoint CPU allocation. Spark retains its 96 GiB heap; each pair has one GPU path. CPU, RAM, filesystem cache, disk and GPU interactions form the shared-host condition. Shared preheat occurs outside timers and does not guarantee residency.

The SF30 pilot has one repetition per pair and suite. The separately gated expansion has two fresh-wave repetitions per pair, suite and SF30/SF100 cell (n = 2 per cell). Each query has one warmup and one measured action per process. These small samples are descriptive; pilot and expansion are shown separately. They supply no new p-values, winner decisions or crossover thresholds.

The protocol parks the isolated scheduler, lets its current worker finish, then requires unchanged source, runtime and input identities before returning to the same scheduler. The original session’s outer orchestration envelope includes this scheduling hold; it is not a query latency and is never rewritten.

Interpretation boundary

Pair B complex has four common measured query pairs. Q13 and window reject translation on strict Polars GPU; their CPU-only measured actions are unpaired diagnostics. A six-query CPU sum would mix conditions and is not a uniformly contended suite score. The pairs have different competing workloads, so they do not rank the two GPU engines.

Contention findings remain unpublished until a genuine terminal replay verifies the original worker payload, separation of action intervals and return to the same isolated-study scheduler. This methods preview includes no timings.

Actual per-repetition action and common-host-result durations, in seconds. Action timers exclude startup and rendezvous waits. Unavailable actions receive no imputed time. Process counter deltas can include untimed rendezvous waits; sampled memory can miss transient peaks, and board GPU utilization cannot identify a causal query contribution.

Inspect actual common-query overlap on both clocks

Intersection is recomputed from saved action intervals on the same-host monotonic clock and UTC clock. Positive process-lifetime overlap alone is insufficient. Start skew is the absolute difference between the two measured action starts.

04 / Experimental frame

What the experiment holds fixed.

One host. Five configurations.

Four execution paths share one H100 80 GB HBM3 host with 26 Xeon Platinum 8480+ vCPUs and approximately 221 GiB of RAM. A second CPU Polars version separates the GPU-compatible baseline from a current CPU control.

Spark uses a 96 GiB driver heap; Polars has no equivalent fixed host-memory limit. The same host does not imply equal memory budgets. This is a comparison of configurations, not an isolated causal effect of the GPU.

01

Fresh sessions, paired blocks

Ten fixed blocks contain all eight suite/scale conditions and five configurations: 400 sessions. Three measured actions follow warmup inside each session. Their median summarizes the query; the ten paired block ratios supply inference. The design does not treat thirty inner actions as thirty independent replicates.

02

Shared inputs, explicit timing

All engines read the same frozen Snappy Parquet inputs. Full byte checks run outside measured work. A preheated filesystem policy is used without an application DataFrame cache; preheating does not guarantee that every page remains in memory. Action time excludes startup. Common-host-result time is a descriptive endpoint sensitivity.

03

Correctness and execution coverage

Every successful warmup and measured output is compared with independent SQL references. Monetary and quantity expressions use Float64/DOUBLE with declared reduction tolerances. Strict Polars GPU rejects CPU translation fallback. GPU Spark can retain CPU operators; saved final plans describe coverage, not the fraction of runtime on GPU.

04

A separate JVM recovery cohort

The initial replacement campaign stopped after 88 validated sessions when CPU Spark reported a Java heap-space allocation failure during warmup. The log also contained a GCLocker retry warning; it does not prove a root cause. Its observations are retained and excluded from the recovery estimates.

The recovery fixes GCLockerRetryAllocationCount=100 for both Spark configurations, retaining Java 17.0.20.1, G1, the 96 GiB heap and the other recorded settings. Startup flag dumps verify the actual JVM configuration. The 52-file experimental source and 1,654 physical input files stay unchanged. This study measures that recovery profile; it does not estimate the causal benefit of the JVM options.

The earlier lost instance’s 120 surviving sessions are also excluded. Off-host backup pauses occur between complete blocks while engines are stopped. Readiness checks establish readiness, not performance.

Scope of interpretation

Conditional evidence for one host, these queries, these versions, and these settings. The study does not establish distributed scaling, equivalent-cost performance, energy efficiency, optimal per-engine tuning, or controlled cold-cache latency. Historical A100/H100 comparisons also change CPU allocation, software, and file layout.
