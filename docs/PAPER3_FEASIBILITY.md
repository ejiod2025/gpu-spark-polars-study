# Paper 3 feasibility audit of the archived telemetry (blinded, structure only)

Status: audit complete; plan not yet locked. Branch `H100_Test`. Generated by `tools/paper3_feasibility.py`
(tests: `tests/test_paper3_feasibility.py`). Reproduce with

    .venv/bin/python -I tools/paper3_feasibility.py --json /tmp/paper3_feasibility.json

The run is deterministic (two runs produce byte-identical text and JSON) and takes about 3 s, including a SHA-256 check of
every file it reads (289 per host) against `results/campaign-20261030/raw-manifests/FINAL-<host>.SHA256SUMS`.

## What this is and is not

Paper 3 compares energy and cost per query across CPU and GPU dataframe engines. Before its analysis plan is locked, this audit
asks only whether the archive is structurally able to support a secondary analysis. It reports counts, time offsets, gaps and
timestamp bookkeeping. It never computes or prints a power, energy, utilisation, temperature, clock, memory or cost value, and
it never ranks or compares engines.

Blinding, as enforced in code:

* Telemetry columns read: `gpu.csv` timestamp, index, and `power.draw` for a count of missing / N-A / unparseable rows only;
  `host.csv` timestamp_utc, scale, engine, phase. Every column is read as text under an explicit schema and parsed by an
  expression whose failures are counted (no type inference).
* `results.json` `seconds` is used only to form differences and ratios against timestamps (window overhead, unexplained time).
* Unexplained time and window uncertainty are pooled over hosts and engines and split by scale only.
* `assert_blinded` rejects any report key naming power, energy, watt, joule, utilisation, temperature, clock, memory, cost,
  speedup or rank. The tests plant a distinctive power value and query time in synthetic data and prove they never reach the
  report.

Incidental exposures during development are listed in the last section.

## Data audited

Four hosts (`h100`, `gh200`, `a100`, `b200`; instance labels `gpu_1x_h100_sxm5`, `gpu_1x_gh200`, `gpu_1x_a100_sxm4`,
`gpu_1x_b200_sxm6`), each with 192 engine sessions: 4 rounds x (baseline 5 scales + complex 3 scales) x 4 engines = 128 main,
plus 4 rounds x 2 Polars-version arms x 8 suite-scales = 64 side-study. Each host has 24 suite directories, each with one
`gpu.csv` / `host.csv` pair spanning that suite's sessions. 768 sessions, 96 telemetry pairs, 18,048 query records in all.

## Q1. Clock domain: gpu.csv maps to UTC unambiguously on all four hosts (offset 0 s)

`nvidia-smi` writes local wall time with no zone. Three independent lines of evidence per host, over all 24 suite directories:

1. Containment bracket. The runner starts `gpu.csv` before its first session and stops it after its last, so the GPU stream must
   contain every session window of its suite (`schedule.json`, UTC). That confines local-minus-UTC to
   `[gpu_first - first_start, gpu_last - last_end + 1 s]`. The intersection over 24 suites contains exactly one multiple of 15
   minutes (real zones are multiples of 15 min), namely 0:

   | host | bracket intersection (s) | 15-min candidates |
   |---|---|---|
   | h100 | [-0.051, +0.811] | {0} |
   | gh200 | [-0.015, +0.811] | {0} |
   | a100 | [-0.036, +0.678] | {0} |
   | b200 | [-0.037, +0.791] | {0} |

   The +1 s end slack is the allowance for nvidia-smi's last sample preceding its SIGTERM by one gap; the observed
   `gpu_last - last_end` lies in [-0.322, -0.003] s on all hosts, i.e. within one 0.2 s interval.
2. `nvidia-smi -q` `Timestamp` (whole seconds, local) minus `environment.json` `started_at_utc`: within [-0.97, +0.02] s on every
   host (truncation to whole seconds explains the negative side). A non-UTC zone would show hours.
3. `gpu.csv` first stamp minus `host.csv` first stamp (the latter written with `datetime.now(timezone.utc)`): +6 to +18 ms across
   all 96 suite directories, a tight band consistent with one clock.

No backward step or duplicate stamp exists in any `gpu.csv` (so no DST fall-back or step); `gpu.csv` and the Python UTC stamps
come from one machine clock, so absolute NTP accuracy is irrelevant for within-host alignment. The existing
`analyze_campaign.py` (lines 1595 and 1669) already reads the stamp as UTC; the audit confirms that assumption.

Limit of the evidence: metadata alone bounds the offset to a window 0.7 to 0.9 s wide, not to milliseconds. Sub-second
alignment between GPU samples and query boundaries could only be tightened by correlating activity onsets in the GPU columns
with `schedule.json` / record start times. That needs the memory or utilisation columns and was deliberately not done; it should
be a pre-registered alignment check in the Paper 3 plan (onset time only, no magnitudes).

## Q2. Coverage of engine-session windows

Windows: worker (`results.json` started_at_utc to completed_at_utc) and process (`schedule.json` start_utc plus
process_wall_seconds, which adds launch and teardown). Hole = gap above 1.0 s (GPU, nominal interval 0.2 s) or 2.0 s (host,
nominal 1 s); covered fraction = 1 - holes / window, edges included.

| host | GPU rows | sessions, worker window | zero-sample sessions | sessions with a gap > 1 s (worker / process) | min covered fraction | max gap (s) |
|---|---|---|---|---|---|---|
| h100 | 166,159 | 192 | 0 | 3 / 3 | 0.9961 | 2.537 |
| gh200 | 121,875 | 192 | 0 | 3 / 4 | 0.9866 | 2.761 |
| a100 | 204,505 | 192 | 0 | 1 / 1 | 0.9985 | 1.385 |
| b200 | 163,570 | 192 | 0 | 0 / 0 | 1.0000 | 0.276 |

* GPU sampling interval: per-session median 0.200 to 0.201 s on every session; per-session p99 0.201 to 0.278 s (b200 0.256,
  h100 0.278, gh200 0.242, a100 0.228 at most).
* All nine GPU gaps above 1 s fall inside sf100 or sf300 sessions (h100: 3, gh200: 5, a100: 1; the largest is 2.76 s). On gh200 one GPU gap (2.76 s) coincides with a 3.28 s `host.csv` gap in the same session (07:17:13 UTC, round 2
  baseline sf300), i.e. a whole-system stall. Sampler starvation under a saturated CPU is therefore a real, if rare, effect.
  `streams[].gpu_gaps_over_1s` in the JSON names each gap and its session.
* `power.draw` parsed in every row of every file: 656,109 rows, 0 missing, 0 N/A, 0 unparseable.
* `host.csv`: median interval 1.001 s; two stalls above 2 s (a100 3.13 s, gh200 3.28 s). Worker windows shorter than the 1 s
  period legitimately hold no sample: 6 on h100 and 10 on gh200, all baseline sf1 `polars` sessions (the fast hosts). In the
  process window the same applies to 2 (h100) and 9 (gh200) sessions, which therefore have no `execute` phase row.
* Phase cross-check (190 + 183 + 192 + 192 sessions with execute rows): the first `execute` row follows the process start by
  0.001 to 1.001 s and the last precedes its end by 0.0 to 0.998 s, exactly what a 1 Hz sampler gives; no `execute` row lies
  outside its process window (tolerance 1.5 s). `host.csv` phase labels exist only at session level; they cannot localise
  individual queries.

## Q3. Per-query reconstruction: possible, and the brief's premise is wrong

Correction to the brief: each `records[]` entry in these archives carries `started_at_utc` and `ended_at_utc` (UTC, written by
`worker.py` around each query), and every cleanup record has `started_at_utc` / `ended_at_utc` too. Per-query windows therefore
do not have to be inferred from sums of durations.

Presence in the archived trees (`pooled.record_stamp_presence` in the JSON): 18,048 of 18,048 records have both stamps, in
every one of the 32 host x suite x scale cells (4 hosts x baseline sf1/10/30/100/300 and complex sf30/100/300; main and
side-study pooled), and none has a window shorter than its timed `seconds`. Provenance: `environment.json` records the
`worker.py` SHA-256 of each suite directory; it is `d1a3cf68...520a1` in all 96 directories on all four hosts, which is the
committed `worker.py` at HEAD (its history shows the stamps in the initial import commit). The uncommitted working-tree
`worker.py` additionally writes `timed_start_utc`, `timed_end_utc` and `timed_start/end_monotonic_ns` around the timer; none of
the archived records has them (0 of 18,048), so the archive offers the wider window only, never the tight timed interval.

How much wider the window is than `seconds` (measured windows, pooled over engines and rounds):

|---|---|---|---|
| h100 | 3,384 | 0.0105 / 0.047 / 0.071 / 0.138 | 0.86 % / 33 % |
| gh200 | 3,384 | 0.0082 / 0.055 / 0.096 / 0.117 | 1.2 % / 86 % |
| a100 | 3,384 | 0.0234 / 0.076 / 0.124 / 0.351 | 1.4 % / 58 % |
| b200 | 3,384 | 0.0116 / 0.047 / 0.069 / 0.152 | 0.86 % / 27 % |
| baseline suite | 8,640 | 0.0082 / 0.051 / 0.092 / 0.335 | 1.8 % / 61 % |
| complex suite | 4,896 | 0.0185 / 0.068 / 0.116 / 0.351 | 0.45 % / 16 % |
| all, by scale | see the scale table below | | |

The width is host- and suite-dependent in seconds (complex and a100 are about two to three times the others at the median; the
archive does not say why) but never exceeds 0.36 s. In relative terms it is large only where the query itself is short (sf1, sf10).

Timeline closure (hosts and engines pooled; 720 sessions without query errors; the 48 sessions with the expected GPU-unsupported
errors are excluded because a failed attempt has only an end stamp):

|---|---|---|
| launch to worker start | `launch_to_engine_ready_seconds - session_and_table_setup_seconds` | closure error -0.001 to +0.002 s (all 768 sessions) |

| gaps between consecutive explained intervals | | 23,040 gaps: p50 2.1 ms, p99 25 ms, max 1.76 s (51 gaps above 0.1 s, 0.2 %) |
| completed_at_utc to process exit (teardown) | not recorded | p50 0.59 s, p90 4.4 s, p99 22 s, max 38 s |

Unexplained time by scale (worker span minus setup, record windows, cleanup windows), seconds: sf1 p99 0.054; sf10 p99 0.055;
sf30 p99 0.68; sf100 p99 0.83 (max 1.29); sf300 p99 3.5 (max 4.7). As a fraction of the session: p99 4.6 %, 1.2 %, 2.5 %, 0.7 %,
1.0 % respectively. Teardown after the worker finishes is the one large unrecorded piece: p99 3.8 s at sf1 rising to 35 s at
sf300 (max 38 s). It matters for session-level energy because the process is still alive and the GPU context still being
released; the plan must say whether it is in or out of scope.

Per-query window uncertainty, measured windows only (13,536; warmups excluded). Overhead is `ended_at_utc - started_at_utc -
seconds`: samplers' start and stop, result conversion, plan serialisation. Over all measured windows it is p50 12 ms, p90 60 ms,

the tool) found the engine's SQL-execution start events 14 to 273 ms after the window start and the SQL end 2 to 47 ms before
its end, so the stamps bracket the engine's own execution tightly.

|---|---|---|

The 1 s column applies to h100, gh200 and b200, where `power.draw` is a 1 s trailing average; on a100 it is instantaneous and only the
sampling column applies (the table pools all four hosts). The semantics differ by host; see the next section.

### What `power.draw` means on each host (semantics only, no values)

Evidence held in the archive, identical in all 24 `environment.json` of each host (`nvidia-smi -q`, section "GPU Power
Readings", which is the board reading; no legacy unlabelled "Power Draw" line exists in any of them):

| host | GPU (architecture) | driver | `Average Power Draw` | `Instantaneous Power Draw` |
|---|---|---|---|---|
| h100 | H100 80GB HBM3 (Hopper) | 580.105.08 | numeric | numeric |
| gh200 | GH200 480GB (Hopper) | 570.148.08 | numeric | numeric |
| a100 | A100-SXM4-40GB (Ampere, GA100) | 570.148.08 | N/A | numeric |
| b200 | B200 (Blackwell) | 570.148.08 | numeric | numeric |

Documentation consulted (NVIDIA pages fetched 2026-11-11): the nvidia-smi page (`-q` attribute descriptions and changelog) and the
NVML API reference for `nvmlDeviceGetPowerUsage`:

* nvidia-smi `-q`: "Average Power Draw: The average power draw for the entire board for the last second, in watts. Only supported
  on Ampere (except GA100) or newer devices." "Instantaneous Power Draw: The last measured power draw for the entire board, in
  Watts." So a trailing 1 s window, and GA100 (the A100) is the documented exception, matching its archived `N/A`.
* NVML `nvmlDeviceGetPowerUsage`: "On Ampere (except GA100) or newer GPUs, the API returns power averaged over 1 sec interval. On
  GA100 and older architectures, instantaneous power is returned." The same entry points to `NVML_FI_DEV_POWER_AVERAGE` and
  `NVML_FI_DEV_POWER_INSTANT` for a specific reading.
* nvidia-smi changelog: `power.draw.average` and `power.draw.instant` were added between v525 and v530 (all four archived drivers
  are newer); between v570 and v575 `-q` was changed to "print both 'Instantaneous Power Draw' and 'Average Power Draw' in all
  cases where 'Power Draw' used to be printed" (the archived 570.148.08 and 580.105.08 output already prints both).

Conclusion on what the archived column (`--query-gpu=...power.draw...`, header `power.draw [W]`) is:

| host | `power.draw` is | basis |
|---|---|---|
| h100 | trailing 1 s average | Hopper is "newer than Ampere"; both fields numeric; NVML doc |
| gh200 | trailing 1 s average (GPU board only, not the module) | same; `Module Power Readings` is a separate section (numeric only on gh200) |
| a100 | instantaneous | GA100: average field `N/A`; NVML doc says instantaneous on GA100 |
| b200 | trailing 1 s average | Blackwell; both fields numeric; NVML doc |

What is not verified. (1) The `nvidia-smi --help-query-gpu` description of the bare `power.draw` field is not on the fetched page and
could not be retrieved (search engines blocked), so the claim that bare `power.draw` follows `nvmlDeviceGetPowerUsage` rests on the
changelog (the new `.average` / `.instant` fields were added alongside it, and `-q` later printed both wherever the single
"Power Draw" used to appear) and on NVML's own documentation, not on the `--help-query-gpu` text itself. For A100 the conclusion
does not depend on that mapping: the average is `N/A`, so the only quantity the driver can supply is instantaneous. (2) The pages are
the current revisions (copyright 2011-2026), not per-driver editions; the architecture rules quoted have been stable, but they were
not checked against the 570 and 580 editions specifically. (3) B200's `Power Smoothing` reads "Insufficient Permissions" (N/A on the
other three), so whether a smoothing profile shaped the B200 power trace is unknown. The definitive empirical test is cheap and
should be in the new campaign's preflight: on each host, sample `power.draw`, `power.draw.average` and `power.draw.instant` together
for a minute under a ramp and record which one `power.draw` tracks.

Consequence: a 1 s trailing average smears every boundary by up to 1 s and shifts apparent timing by about half a second; on A100 the
column is instantaneous and unsmoothed. Any cross-host reading of that column mixes two measurement semantics and needs a caveat
(Paper 1 included). The archive cannot show how large the effect is without reading values, which this audit did not do.

Verdict: per-query windows can be rebuilt to within about 0.1 s of overhead on all hosts. Whether per-query GPU energy is
meaningful depends on scale: below sf30 virtually no query spans enough samples, and even at sf300 about 36 % of windows have
fewer than 25 samples (under about 5 s).

## Q4. Completeness

* Hosts x suites x scales x engines x rounds: 192 / 192 sessions on every host, none missing, none unexpected; 24 / 24 suite
  directories each with `gpu.csv`, `host.csv`, `schedule.json`, `environment.json`; 8 / 8 `attempt.json` and `gates.json`, 4 / 4
  preflight reports. The side study is complete in every round (4 rounds, both arms, both suites); the per-round
  `side-study__round-4` manifest is missing for h100 and gh200 but `FINAL-<host>.SHA256SUMS` lists all side-study rounds.
* Telemetry integrity: headers exact (GPU: 9 columns as in `GPU_TELEMETRY_QUERY`; host: 9 columns); every file ends with a
  newline; 0 incomplete rows, 0 unparseable timestamps, one GPU index (0) everywhere; `gpu_telemetry.started` is true in every
  `environment.json`. Streams contain every session window of their suite (end slack 1 s). Zero host.csv stamps lack the
  fractional second (a silent-parse trap the reader handles anyway).
* Records: 4,512 per host = 192 sessions x 24 attempts (6 queries x 1 warmup + 3 measured) minus 24 failed queries x 4
  attempts; 24 query errors per host, all on the queries listed in `design.expect_gpu_unsupported`; per the worker, a query whose warmup fails is dropped from the measured trials, so those
  sessions legitimately have fewer records. 0 unexpected errors, 0 sessions with a non-zero return code.
* Integrity: every file the audit read (289 per host) matches `FINAL-<host>.SHA256SUMS`; 0 mismatches, 0 files read but
  unlisted, 0 manifest entries missing on disk, 0 tree files absent from the manifest (the manifest itself excepted). The
  `results/campaign-20261030/raw-manifests` copies are git-tracked and byte-identical to the in-tree ones. This establishes
  that the archive matches its manifest, not that the manifest was produced faithfully on the remote host.
* Problems flagged (all hosts): 11 sessions without a `host.csv` execute row (baseline sf1 `polars`, shorter than the 1 s
  period), nothing else. a100 and b200 are fully clean.
* Not covered by any telemetry: the time between suites (each suite has its own `gpu.csv`) and, for round 1, the pause before
  the resumed invocation. Neither contains sessions.

## Q5. Recommendation

Feasible secondary analyses of the archive (descriptive, hypothesis-free; the plan must say so):

1. Session-level GPU board energy over the process window, all 768 sessions: coverage is at least 98.7 % everywhere and 100 % on
   b200. Pre-register treatment of the 8 sessions with a gap above 1 s (exclude or flag; do not interpolate silently), the
   teardown rule (up to 38 s of the process window is exit time), and the A100 versus other-hosts `power.draw` semantics.
2. Per-query GPU energy for measured windows with at least about 25 samples, in practice sf100 and sf300 and long complex
   queries (roughly 3,400 of 13,536 measured windows; about 960 have at least 100 samples). Not for sf1 and sf10. State the
   boundary uncertainty per scale from the table above, and a shift convention for the 1 s average.
3. GPU idle draw during CPU-engine sessions (the GPU stays in the host; `gpu.csv` covers CPU sessions too), as a fixed
   hardware term in a like-for-like comparison.
4. Cost per query and per session from wall-clock windows times a stated hourly price. Timing and window data are complete; the
   archive stores only instance labels, no price, region or billing quantum, so prices must come from outside and be dated.

Not possible from the archive, so the new campaign must measure it:

* CPU, DRAM or whole-node power for the CPU engines (`polars`, `spark_cpu`) and for the CPU side of the GPU engines. Nothing
  in the archive captures RAPL, a BMC or a wall meter (searched all four trees), and three of four hosts are KVM guests where
  RAPL is usually not exposed. `host.csv` has only `cpu_percent` at 1 Hz; turning it into power would be a model, not a
  measurement. Without this, "energy per query, CPU versus GPU" is not answerable from the archive.
* Per-query energy independent of the sampler: a cumulative GPU energy counter (NVML total energy, millijoules) read in process at
  each query's start and end, instead of integrating sampled power, which removes the 0.2 s sampling and 1 s averaging limits.
* Query boundaries in the same clock domain as the telemetry (monotonic stamps recorded in the stream, or a marker row), so the
  alignment check in Q1 is unnecessary.
* Both `power.draw.average` and `power.draw.instant` where the driver offers them, with the driver version, on every host.
* A sampler that survives a saturated CPU (nine stalls above 1 s, up to 2.8 s, in this archive); record its own lag.
* Matched idle baselines before and after each session, and process-exit time with sampling continued until the GPU is idle, so
  teardown energy is attributable.
* Longer measured units at small scale (repeat inside one window) if sf1 to sf30 are to be in scope at all.
* Billing metadata (instance type, region, hourly price, billing quantum, date).

An in-progress `power_telemetry.py` and edits to `run_experiment.py` / `worker.py` that appeared in the working tree during this
audit appear aimed at several of these points; they were not reviewed here.

## Incidental exposures and limits of this audit

Blinding-breach note, verbatim as reported to the team lead:

> **Blinding breach: yes, minor**
>
> Before I switched to timestamp-only readers I printed raw rows from the h100 round-1 baseline suite:
> - The first two and last two `gpu.csv` rows. These were idle rows outside any session, with one power, utilisation, memory, temperature and clock reading each.
> - The first two and last two `host.csv` rows. These included `cpu_percent` and memory fields for one `spark_cpu` sf1 and one `polars` sf300 execute-phase sample.
> - The head of that suite's `schedule.json`, which showed `process_wall_seconds` for one `spark_cpu` sf1 session.
>
> I computed no aggregate by engine, host or scale from any of it. The pooled per-scale overhead and sample-count tables you requested inherently reflect the pooled query-time scale, with no engine contrast.
>
> For the follow-up, I printed the `nvidia-smi -q` power sections with every numeric value masked, so no power value was read. The files `t16_energy_proxy.csv`, `t24_gpu_telemetry.csv` and the Paper 1 Power column were not opened.

Details and further limits:

* While exploring file layout I printed raw rows that include outcome columns, before settling on the timestamp-only readers:
  the first two and last two rows of `rerun/hosts/h100/.../round-1/baseline/gpu.csv` (idle rows outside any session: one power,
  utilisation, memory, temperature and clock reading each) and the first two and last two rows of the matching `host.csv`
  (including `cpu_percent` and memory fields of one `spark_cpu` sf1 and one `polars` sf300 execute-phase sample), plus the head
  of that suite's `schedule.json` (the `process_wall_seconds` of one `spark_cpu` sf1 session and the first `polars_gpu`
  entry's start). No aggregate by engine, host or scale was computed from any of these. The pooled per-scale overhead and
  sample-count tables in Q3 inherently reflect the pooled query-time scale; they were requested, are pooled over engines and
  hosts, and contain no engine contrast.
* Per-session "no execute rows" and gap listings carry the session id (including the engine), which is needed to act on them.
* Committed per-engine GPU power summaries already exist in the repository (`t16_energy_proxy.csv`, `t24_gpu_telemetry.csv`,
  and a Power column in Paper 1). They were not opened, per the blinding rules. Consequence for the plan: any Paper 3 analysis of
  archived GPU power is not blind with respect to engine-level GPU power, whatever this audit did; only the new campaign can be
  pre-registered blind. The existing t24 analysis excludes actions shorter than 1 s, per its test file's description.
* Not done: any use of utilisation or memory columns for activity-onset alignment; any look at Spark event logs beyond the one
  spot check; any review of the new instrumentation code.
